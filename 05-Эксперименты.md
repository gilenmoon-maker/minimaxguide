# 05 — Экспериментальная лаборатория

## Цель

После baseline мы не угадываем, какая модель лучше. Мы запускаем одинаковые тесты и сравниваем результаты.

---

# 1. Правило честного сравнения

Для сравнения двух вариантов максимально фиксируем:

- исходную картинку;
- prompt;
- seed, если он применяется одинаково;
- разрешение;
- длительность;
- steps;
- scheduler;
- sampler;
- post-processing.

Меняем только то, что хотим проверить.

---

# 2. Эксперимент Qwen 8-bit vs 4-bit

## Цель

Понять, насколько сильно меняется результат из-за квантизации encoder.

## Тест

```text
H3 = одинаковый
Prompt = одинаковый
Image = одинаковая
Resolution = одинаковая
Duration = одинаковая
Steps = одинаковые

Qwen 8-bit → результат A
Qwen 4-bit → результат B
```

## Оцениваем

- понимание prompt;
- сохранение лица;
- сохранение композиции;
- движение;
- время;
- VRAM;
- RAM.

---

# 3. H3 INT8 vs W4

Сначала выбираем лучший Qwen.

Затем:

```text
H3 INT8
   vs
H3 W4
```

Не меняем остальные параметры.

---

# 4. H3 W4 vs INT4

Следующий тест:

```text
W4
 ↓
INT4
```

Наша задача — определить, стоит ли экономия памяти потенциальной потери качества.

---

# 5. INT4Q

Отдельный community test.

Записываем:

- источник;
- commit/дату;
- формат файла;
- loader;
- workflow;
- требования автора;
- результат;
- ошибки.

Нельзя просто назвать его «INT4» и считать идентичным другому INT4.

---

# 6. INT4BQ

То же самое.

Сравниваем непосредственно с другими INT4 только после того, как убедились, что loader и pipeline корректны.

---

# 7. W4A8

Отдельный эксперимент.

W4A8 не нужно смешивать с обычным W4 workflow.

Нужен совместимый loader/backend.

Community project:

https://github.com/starsFriday/ComfyUI-W4A8-Loader

Перед установкой читать README именно текущего commit/release.

---

# 8. GGUF

GGUF тестируем отдельной серией.

Примерная матрица:

```text
Q2
Q3
Q4
Q5
Q6
Q8
```

Не обязательно тестировать всё, если более высокий вариант уже не помещается или не даёт практической выгоды.

### Волосы

0–3.

0–3.

# 13. Тест разрешения

После стабильного короткого видео:

```text
низкое
 ↓
768p-class
 ↓
более высокое
```

Не повышаем одновременно разрешение и длительность.

Иначе будет непонятно, что именно вызвало OOM или резкое замедление.

---

# 14. Что означает «лучшая модель»

Не обязательно самая качественная.

Допустим:

| Модель | Время | Качество |
|---|---:|---:|
| A | 2 мин | 7/10 |
| B | 5 мин | 8/10 |
| C | 20 мин | 8.2/10 |

Для нашего проекта B может быть лучшим вариантом.

Но если C даёт уникальное качество, которого не дают A/B, C остаётся полезной для отдельных сцен.

---

# 15. Практическая система профилей

После тестов создаём:

### FAST

Самая быстрая рабочая модель.

### BALANCED

Лучшее качество/время.

### QUALITY

Самая тяжёлая модель, которую реально использовать.

### EXPERIMENTAL

Новые community quants.

---

# 16. Turbo LoRA

Community MiniMax H3 ComfyUI проект также описывает Turbo LoRA для ускорения генерации. Он заявляет до 2× ускорения с небольшими потерями качества, но это отдельный путь, который нужно тестировать после базового workflow. citeturn0search3

Для нашей лаборатории:

```text
Baseline
 ↓
Turbo LoRA
 ↓
сравнение качества
```

Не используем Turbo LoRA для первоначального сравнения разных quant, иначе сравнение будет смешанным.

# 17. Как документировать эксперимент

Каждый тест сохраняем как:

```text
experiments/
└── 2026-08-19_INT4_vs_INT8/
    ├── prompt.txt
    ├── settings.txt
    ├── input.png
    ├── output_int4.mp4
    ├── output_int8.mp4
    └── result.md
```

---

# 18. Статусы

Используем:

- `PASS` — работает;
- `PASS-SLOW` — работает, но слишком медленно;
- `PASS-GOOD` — хороший баланс;
- `OOM` — не хватает памяти;
- `ERROR` — техническая ошибка;
- `BAD-QUALITY` — работает, но результат неприемлем;
- `EXPERIMENTAL` — ещё не проверено достаточно.

---

# 19. Никогда не делаем вывод по одному запуску

Один ролик может случайно получиться лучше.

Минимум:

**3 разных prompts**

для первичной оценки.

Лучше:

**5–10 сцен.**
